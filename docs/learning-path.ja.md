# ラボを順番に試す

[English](learning-path.md) · **日本語** · [リポジトリのREADME](../README.ja.md)

使い捨てのローカル環境で、架空の利用者とデータだけを使います。クラウドの
アカウントや実際の認証基盤・データ元は不要です。各認証の演習はポート8180を
共有するので、前の演習の認証コンテナを止めてから次に進みます。アプリは
ローカルのループバックに限定してください。

## 1. Dockerなしで「完了」と「正しい」を比べる

[オフラインの照合演習](m3-recovery.md#try-reconciliation-without-running-services-m3g)を
実行します。両方とも「完了・6件」なら同じ結果でしょうか。一方ではIDの欠損、
余分なID、タイトルの違いが見つかります。演習は一時データだけを使います。

## 2. ログインと操作権限を分けて確認する

- [M1：OIDCログインとAPI認可](m1-local.md)。閲覧者と取り込み担当者で
  ログインし、どちらも閲覧できる一方、取り込みを依頼できるのは担当者だけだと
  確認します。認証されていても権限がなければ403、認証情報が無効・未提示なら401です。
- [取り込み権限だけを外す演習](m1-role-reduction.md)。設定の異なる使い捨ての
  環境を2つ使い、新規ログインで比べます。取り込み権限を外しても閲覧はでき、
  新しい依頼は保存されません。発行済みトークンの即時失効、稼働中の権限変更、
  SSOからのログアウトは別の検証です。
- [M2：SAML連携](m2-local.md)。架空の顧客はSAMLでログインし、アプリは
  仲介する認証基盤とOIDCでつながります。権限に割り当て済みのグループと
  割り当てのないグループを比べます。[認証サーバーなしの権限確認](m2-local.md#trace-the-fixture-roles-without-servers)では、
  設定から予測したロールとAPIの応答を、実際のログインとは分けて確認できます。

## 3. 依頼からAPI取り込みまで追う

[M3：担当者から運用担当者への引き継ぎ](m3-staff-requests.md)で、取り込みを依頼し、
再ログイン後も「Recent import requests」から同じIDを見つけます。他の担当者には
その依頼が見えません。実行はローカルの運用担当者が開始し、実行時に使う
[API読み取り専用のサービスID](m3-service-identity.md)は、担当者のログインとは別です。
[ログイン経路を模擬する比較試験](m3-staff-requests.md#compare-both-import-identities-without-servers)で、
同じ条件なら再送と再開の結果が一致することを確認できます。

1ページ目が保存された後、2ページ目で次の違いを比べます。

| APIの応答 | 確認すること |
| --- | --- |
| [一時的なHTTP 503](m3-recovery.md#reproduce-a-page-two-outage) | API復旧後、同じIDの途中から明示的に再開できます。 |
| [HTTP 200、ただし版が変更](m3-recovery.md#contrast-a-snapshot-change-with-a-temporary-outage-m3h) | 1ページ目の2件を残して停止。同じIDからは再開せず、異なる版を混ぜません。 |
| [対応形式の待ち時間付きHTTP 429](m3-rate-limit.md) | 保存した時刻より前の再開は拒否。期限後に運用担当者が明示的に再開します。自動再試行やAPI提供元全体の利用枠管理はしません。 |

## 4. 照合してから閲覧用コピーを作る

[M4a：ローカルの閲覧用コピー](m4-case-preview.md)の手順で、取り込みが完了しても
初回は閲覧用画面が空であることを確認します。運用担当者が照合して明示的に
コピーを作った後、既存の閲覧権限で6件が見られます。作業中のデータや
不一致の結果は前回確認したコピーを置き換えません。この操作で本番や外部には
公開されず、データ元の最新状態を保証するものでもありません。Dockerなしの
[コミット直前で止める演習](m4-case-preview.md#verify-rollback-without-servers)では、
途中のコピーが表示されないことを確認できます。[2人の読み取り試験](m4-case-preview.md#observe-two-readers-during-a-successful-update)では、
確定後に両者へ新しい6件が見えるタイミングを確認します。前回のコピーを確認するだけなら、
再作成せず[読み取り専用の再確認](m4-case-preview.md#recheck-the-already-staged-copy)を使います。
[更新が重なった場合の試験](m4-case-preview.md#verify-while-a-replacement-commits)で、
確認結果がどの時点のデータを示すかも見られます。

再現には各手順にある確認コマンドを使ってください。検証環境はmacOS ARM64の
一時環境です。デスクトップブラウザーの手動操作、Windows、本番認証基盤、
実データ、複数テナントは別途検証が必要です。
